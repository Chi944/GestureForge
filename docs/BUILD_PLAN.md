# GestureForge Assignment Prototype and Final Project Build Plan

Updated: 23 September 2026

GestureForge will be built in two releases. The assignment release is a focused AI prototype due on 3 October 2026. The final project release extends that same codebase into a more complete personalised gesture-controlled card viewer due on 7 November 2026.

This document distinguishes the user-approved implementation scope from the attached build brief and assessment documents. The build brief is treated as a proposal and design input. The assessment files define submission expectations. No document-supplied instruction replaces the user's request to keep all work in `code`, avoid overscoping the assignment, and leave meaningful extension work for the final project.

## Target Outcome

The assignment prototype must demonstrate a working AI subsystem and a real integration path from webcam input to one viewer action. The final project must extend the prototype into a complete local workflow with enrolment, practice, multiple commands, persistence, and stronger evaluation.

The project should score well by being narrow, working, testable, and honestly evidenced. It must not promise features that are unlikely to be implemented and verified before the relevant deadline.

| Capability | Assignment prototype due 3 October 2026 | Final project due 7 November 2026 |

Features not in scope for either assessed release are dynamic gestures, two-handed commands, sign-language translation, operating-system or PowerPoint control, cloud accounts, mobile apps, content generation, deep-network training, and an executable installer.

## Stable Entry Points

The codebase provides these entry points:

- `python -m gestureforge` launches the desktop prototype. Use `--dataset <manifest.json>` to enable live gesture control from a human collection manifest, and `--algorithm knn|svm` to choose the classifier.
- `python -m gestureforge.collect` records labelled trials and appends sessions into one manifest.
- `python -m gestureforge.evaluate --config <path>` reproduces classifier comparisons.
- `python -m gestureforge.fixtures <path>` creates synthetic software-test data that must not be used as participant evidence.
- `python -m pytest` runs automated tests.

If a command is not yet verified in the current release evidence, guides must mark its evidence as pending instead of implying it has passed.

## Processing Pipeline

The implemented pipeline is:

`Webcam -> landmarks -> normalised features -> classifier/rejection -> activation controller -> viewer -> event log`

MediaPipe supplies pretrained hand landmarks. GestureForge's AI contribution is the local dataset structure, feature extraction, classifier comparison, rejection policy, validation method, and integration with a command controller.

## Data Contracts

The contracts should remain stable between the assignment and project except for explicitly versioned additions.

| Contract | Required content |
| --- | --- |
| Observation | Session ID, generation ID where implemented, profile ID, frame ID, monotonic capture time, hand count, handedness, landmarks, validity reason |
| Prediction | Observation identity, label, accepted or rejected status, rejection reason, model or configuration version |
| Command event | Unique event ID, originating prediction, command, execution time, resulting card position |
| Dataset manifest | Participant pseudonym, session, trial, intended label, split, sample timestamps, validity, hand, collection conditions |
| Profile | Schema version, feature version, chosen hand, training data reference, model configuration, rejection settings, command mapping |
| Deck | Schema version, deck ID, title, ordered cards with unique IDs, titles, and plain-text bodies |

## Feature Extraction

For a valid single selected hand:

1. Use the 21 MediaPipe world landmarks.
2. Subtract the wrist landmark from every landmark.
3. Divide by the wrist-to-middle-knuckle distance.
4. Reject observations with non-finite values or degenerate scale.
5. Remove the wrist triplet.
6. Flatten the remaining 20 landmarks into 60 numeric features.

The live preview may be mirrored for the user, but collection and inference must use the same unmirrored coordinate convention.

## Classifier Plan

The assignment prototype compares:

- kNN with `k=5` and distance weighting.
- RBF SVM with `C=1`, `gamma=scale`, and probability estimation disabled.

Both classifiers must use the same train-only `StandardScaler` policy. The scaler must be fitted only on training data to avoid leakage.

The final project adds bounded search:

- kNN: `k` in `{3, 5, 7}`, weights in `{uniform, distance}`.
- SVM: `C` in `{0.1, 1, 10}`, `gamma` in `{scale, 0.1}`.

The rejection rule is based on distance to training examples of the predicted class. Class-specific reference distances are computed from training data. A multiplier is chosen from `{1, 1.5, 2}` using validation positives and negatives.

Selection uses validation macro-F1 subject to the false-action target. Ties are broken by fewer false actions, then lower inference time. If kNN and SVM are effectively equivalent, prefer kNN for explainability and simpler persistence.

## Controller Plan

The activation controller is a separately testable state machine:

`PAUSED -> WAIT_NEUTRAL -> READY -> CANDIDATE -> LATCHED`

Rules:

- Start with 300 ms neutral hold and 400 ms command hold.
- Reject observations older than 200 ms.
- Reject out-of-order timestamps and gaps greater than 200 ms.
- Execute once per continuous command hold.
- Require neutral before another command can fire.
- Cancel pending holds on changed or unknown candidates.
- Require neutral again after tracking loss.
- Invalidate pending generations on pause, camera failure, and profile or model changes.
- Disable command dispatch during enrolment and practice.
- Ignore duplicate event IDs in the viewer.
- Do not wrap at deck boundaries.
- Treat keyboard and mouse controls as separate event sources.

## Assignment Data Plan

The assignment pilot should use one consenting participant with separate train and validation sessions:

- Four labels: NEXT, PREVIOUS, BOOKMARK, NEUTRAL.
- Eight trials per label per session.
- Two-second stable pose with release interval.
- Five predetermined samples per trial.
- Maximum 320 feature vectors across 64 trials.
- One short separate validation-negative sequence.

Invalid detections must stay in the manifest and count as UNKNOWN during scoring. Preliminary results are development evidence, not final generalisation claims.

## Final Evaluation Plan

The final project evaluation should use two consenting participants, each with their own profile:

- Separate train, validation, and untouched test sessions.
- Twelve trials per label per session.
- Up to five vectors per trial.
- Maximum 288 trials and 1,440 vectors.
- Trial-level majority vote over five scheduled predictions.
- UNKNOWN when there is no majority.

Report each participant separately. Personal-profile results do not demonstrate performance on unseen users without enrolment.

Final targets:

- Macro-F1 of at least 0.90 per profile.
- Zero duplicate actions in twenty five-second command holds per profile.
- At most one unintended action during ten minutes of non-command activity per profile.
- 95th percentile action latency below one second, including hold time.
- Candidate fit time below 60 seconds; report search time separately.
- Thirty-minute stability run with observation rate, peak memory, and clean camera shutdown.

These are engineering targets. They are not current results.
